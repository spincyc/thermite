thermite generate

Write conf/ and metrics/ from the house file, and deploy/'s systemd units.

usage: thermite generate [-h] [--config DIR] [--check | --prune] [--house FILE]
                         [--conf DIR]

Generate conf/ from the house file (instance/devices.yaml), metrics/ (the
Prometheus, blackbox_exporter, Grafana and exporter configuration, and the
dashboards) from the house file and the host file (instance/host.yaml), and
deploy/'s systemd units from versions.json and the host file. All three are
generated: change the house file, the host file, versions.json or lib/,
then run this; never edit conf/, metrics/ or deploy/ by hand.

It validates the house file first and writes nothing while it has a
problem. Writing never deletes: a file under conf/ or metrics/ that nothing
generates is reported and makes the exit status 1; --prune removes such a
file when it carries the generated header (an earlier generate wrote it)
and only reports any other.

options:
  -h, --help            show this help message and exit
  --config, --site DIR  use this private configuration directory
  --check               change nothing; exit 1 if conf/, metrics/ or deploy/ is stale
  --prune               also remove files under conf/ and metrics/ with the generated
                        header that nothing generates now
  --house FILE          the house file (default: instance/devices.yaml)
  --conf DIR            the runtime conf directory (default: conf/)

switches every verb takes:
  -q, --quiet           print only errors
  -v, --verbose         also print, on stderr, the commands and HTTP requests it runs
  --no-color            no color in what it prints (as NO_COLOR=1 does)

exit status:
  0  conf/, metrics/ and deploy/ are what the house file, the host file and
     versions.json generate (with --check: and nothing was written)
  1  a file is stale or missing (with --check), or conf/ or metrics/
     holds a file nothing generates
  2  a wrong switch, or a house or host file that is missing, cannot be
     read or has a problem (nothing is generated)

examples:
  thermite generate                 validate the house file, then write every file under conf/, metrics/ and deploy/ that differs
  thermite generate --check         change nothing; name every stale, missing or stray file
  thermite generate --prune         write, and remove generated files nothing generates any more

thermite lint

Refuse credentials in Git, and docs naming a missing make target.

usage: thermite lint [-h] [--config DIR]

Refuse credentials and runtime state in this area's Git content, and docs
that name a make target the Makefile lacks. It runs two checks, and exits 1
if either finds anything:

  - the secret scan: every tracked file and every untracked file Git would
    add. Where Git lists nothing (outside a work tree, or a tree exported
    below an ignored path) it scans every file outside var/ and build/
    instead, so an empty listing never passes. A line that must carry a
    credential-looking word for a documented reason ends with the marker
    `lint: allow`.
  - the docs' make targets: every `make TARGET` that README.md, FAQ.md,
    docs/*.md or site/pages/*.md cite in code must be one the Makefile
    defines.

options:
  -h, --help            show this help message and exit
  --config, --site DIR  use this private configuration directory

switches every verb takes:
  -q, --quiet           print only errors
  -v, --verbose         also print, on stderr, the commands and HTTP requests it runs
  --no-color            no color in what it prints (as NO_COLOR=1 does)

examples:
  thermite lint                     scan the area's files Git has or would add, and check the docs' make targets

thermite test

usage: thermite test [-h] [--config DIR] [--timeout SECONDS] [--house FILE] ACTION ...

Test conf/ on a test runtime, the pinned distribution on 127.0.0.1:13618,
never production: `boot` boots conf/ and reports how it loads (thermite

thermite test boot
usage: thermite test boot [-h] [--conf DIR] [--timeout SECONDS] [--settle SECONDS]
                          [--stall SECONDS] [--rebuild] [--require-online] [--json]
                          [--keep]

Boot conf/ on a test runtime and report how it loads.

Boot a test runtime (the pinned distribution, see thermite sandbox) on
CONF, on 127.0.0.1:13618 (HTTPS 13619, Karaf console 13620) so it can run
beside the sandbox. It boots on var/boot-check/conf, a copy of CONF in which
every HTTP binding channel is READONLY (oh_render.read_only), so it polls the
real matrices but cannot switch them. Wait for the add-ons in
CONF/services/addons.cfg and for Things to settle (none waiting for a
handler, and no status change for --settle seconds, or 2s once every Thing
is ONLINE), then report the runtime version, requested vs installed add-ons,
Things by status/statusDetail, the Item count, model problems (DSL and YAML
files, scripts that fail to load) and other ERROR records from openhab.log,
and that /rest/metrics/prometheus (the Metrics add-on, which Prometheus
scrapes) answers with every runtime series the dashboards chart.
If Things still wait for a handler and neither they nor the start level
change for --stall seconds, stop waiting and fail on them.

The check proves conf/ loads and every Thing gets a handler without a
configuration error. An online, account-free HEOS bridge's optional-login
diagnostic remains a warning; local transport does not require an account.
A Thing still INITIALIZING/UNKNOWN waits for its device
and only warns; with --require-online the check also waits for devices and
fails on any Thing not ONLINE. Device reachability is thermite health's job:
the sandbox's web server is bound to 127.0.0.1, so UPnP event callbacks from
speakers cannot reach it and they may only report at the binding's
60s poll.

Each run starts from a copy of a warmed userdata in var/boot-check/template/
(OSGi cache built, add-ons installed, admin user and API token created), so
runtime starts without downloading anything. The template is built on the
first run and again whenever addons.cfg or a runtime pin changes, or with
--rebuild; that run takes about a minute longer.

A clean run records the digest of CONF's files in var/boot-check/passed/;
thermite deploy installs only a conf/ with such a record.

The instance is stopped at the end unless --keep is given. Its userdata is a
disposable copy, so it is killed if it has not stopped within 3s.

options:
  -h, --help         show this help message and exit
  --conf DIR         the runtime conf directory (default: conf/)
  --timeout SECONDS  seconds to wait for the whole check (default: 300)
  --settle SECONDS   seconds Things must stay unchanged (default: 5)
  --stall SECONDS    stop waiting once Things without a handler and the start level stay
                     unchanged this long (default: 30)
  --rebuild          rebuild the warmed userdata template first
  --require-online   fail on any Thing that is not ONLINE
  --json             print the report as JSON
  --keep             leave the instance running afterwards

switches every verb takes:
  -q, --quiet        print only errors
  -v, --verbose      also print, on stderr, the commands and HTTP requests it runs
  --no-color         no color in what it prints (as NO_COLOR=1 does)

exit status:
  0  clean
  1  model problems in openhab.log, requested add-ons not installed, or a
     Thing UNINITIALIZED or in HANDLER_CONFIGURATION_PENDING /
     CONFIGURATION_ERROR (with --require-online: any Thing not ONLINE)
  2  the instance could not be booted or queried

examples:
  thermite test boot                boot conf/ on a test runtime and report how it loads
  thermite test boot --require-online
                                    also wait for every device, and fail on any Thing not ONLINE
  thermite test boot --json --keep  the report as JSON; leave the instance running
thermite test routing
usage: thermite test routing [-h] [--timeout SECONDS] [--house FILE]

The room Source selectors end to end, against simulated matrices.

Prove the room Source selectors work, end to end, without touching the
house. Generate conf/ from the house file, keep only what routing needs
(the model, the matrix and HDMI switch Things, rules and Items, the Source
selectors and routing.js, All off), point those Things and rules at
simulated matrices on 127.0.0.1 (lib/oh_matrix_sim.py), simulate the rooms'
receivers, displays, source power and actions with plain Items that take
what they are sent, boot a test runtime on that as thermite test boot does,
and check that:

1. each room's Source reads back what its HDMI switch and HDMI output show,
   and runtime wrote nothing to a matrix while it started;
2. choosing every source a room offers (all rooms at once, round by round)
   routes the room's HDMI output, HDMI switch and USB device ports as the
   routing says, wakes the chosen source, powers its receiver and display
   (off for Off) and puts them on their inputs, sends its actions, has each
   source's input present the EDID of a room showing it (the idle EDID
   once none does), and a choice the room does not offer sends nothing;
3. a switch made at the matrix, at a room's HDMI switch (a keypad, the
   front panel, a web page) or at its receiver or display shows up in that
   room's Source, an input the room does not offer shows as UNDEF, a
   receiver or display turned off there shows as Off, and runtime writes
   nothing for any of them;
4. with two rooms on one source, the last to choose it wins, the first
   gets it back when that room turns off, and the idle EDID follows once
   neither shows it;
5. the rooms go UNDEF while the HDMI matrix, or their HDMI switch, does not
   answer, and recover without a write;
6. the remote page (web/remote) is served at /static/remote/ and, with no
   login, as a phone uses it, reads a room's Source, sends a choice and
   hears it read back on the event stream;
7. All off, sent as the page sends it, turns every room Off as a choice
   of Off would (all_off.js; devices outside the routing are omitted);
8. the simulated matrices heard only the comheads each Thing or rule may send (no
   fixed setting such as scaler or HDCP) and refused none;
9. openhab.log holds no ERROR and no model problem.

warmed userdata, so it cannot run beside it.

thermite test controls
usage: thermite test controls [-h] [--timeout SECONDS] [--house FILE]

Receiver, streamer, projector and TV controls, plus Sonos Item contracts, against stand-ins.

Prove the remote and routing controls work, end to end,
without touching the house. Generate conf/ from the house file, keep only
the Things, Items and rules of the devices runtime controls (every
integration's remote(), plus its stage() input where the page has no input
selector), point each at a simulated device on loopback with

does, and check that:

2. every Thing is ONLINE, every control Item reads what its simulated
   device shows, and runtime sent them no command while it started;
3. power, every input, a volume, mute and every remote key reach the
   simulated device as that device's own command, and are read back;
4. a volume above the configured limit is held to it. A full-range Sonos
   Dimmer reaches 100 and rejects 110 at REST without a device write;
   an unknown key sends nothing;
5. each device's Mute (Input on a projector), pressed as the page presses
   it, reaches its simulated device within REACH seconds and is read back on the
   page's event stream within its integration's READ_BACK plus SLACK; the
   log shows every time and the CPU runtime used meanwhile;
6. with no login, as a phone uses it, a command is accepted and its
   read-back heard on the remote page's event stream (all its topics);
7. All off, pressed as the page presses it, turns every device with a
   power control off (all_off.js; the rooms' Source Items are not in this
   conf, so it names them as missing);
8. openhab.log holds no ERROR and no model problem.

power or playback feedback. Unknown keys never enter the native MAP lookup.

Its result must acknowledge that new command, and neither native log may
record the pairing command or its PIN.

HTTP, with fake UDNs. This checks profiles, keys, limits and UI read-back;
it does not simulate or claim native Sonos UPnP/SOAP protocol coverage.
Native discovery/channel status and idempotent real-binding validation are
separate deployment checks.

thermite sandbox

Run a thermite sandbox from a copy of conf/ on 127.0.0.1:13615.

usage: thermite sandbox [-h] [--config DIR] ACTION ...

Run a local runtime sandbox from the distribution zip and a Temurin JRE, both
pinned in versions.json and cached under build/sandbox/. No root, container
runtime or system Java is needed.

The sandbox binds HTTP to 127.0.0.1:13615 and HTTPS to 127.0.0.1:13616
(OPENHAB_HTTP_ADDRESS/OPENHAB_HTTP_PORT/OPENHAB_HTTPS_PORT, honoured by
runtime/bin/setenv), so the UI is not reachable from the LAN (but see
--live below). The Karaf
console listens on 127.0.0.1:13617. Bindings still open UPnP/mDNS sockets on
the LAN.

It runs on var/sandbox/conf, a copy of conf/ in which every HTTP binding
channel is READONLY, every Item linked to a channel that could command a
device is display-only and every rule's SEND is off (oh_render.read_only):
it reads the matrices and the devices under control but cannot command them.
`reload` refreshes the copy after `thermite generate`; the running sandbox
picks the change up.

`start --live` is a test instance for the house instead: its copy of conf/
is unchanged, so its Source selectors switch the real matrices and its
remote drives the devices under control (the Apple TVs through thermite
apple-tv serve; every other control stays guarded in conf/), and HTTP and HTTPS
listen on every interface, so phones on the LAN reach it on port 13615 of
this host. Anyone on the LAN can then do what the runtime's implicit 'user' role
allows, choosing sources and driving those devices included; administration
still needs the admin login. `reload` keeps the mode the sandbox was started in;
stop and start it to change modes. It refuses to start while production runtime runs
on this host (it answers on 127.0.0.1 at instance/host.yaml's http_port, or
thermite-openhab.service is up): two live instances would fight over the same
devices and pairings. It cannot see a production runtime on another host;
make sure none runs before starting one.

State lives in var/sandbox/: conf/, userdata/ (the runtime's userdata, initialised
from the distribution template when empty), openhab.pid, console.log,
api-token and admin-password.

options:
  -h, --help            show this help message and exit
  --config, --site DIR  use this private configuration directory

actions:
  ACTION
    fetch               download, verify (sha256 from versions.json) and extract JRE +
                        distribution
    start               start the sandbox in the background and wait for REST
    reload              refresh var/sandbox/conf from conf/, in the mode the sandbox
                        started in
    stop                stop gracefully (SIGTERM), SIGKILL after --timeout
    status              report whether the sandbox runs and REST answers (exit 3 if
                        stopped)
    logs                show userdata/logs/openhab.log

switches every verb takes:
  -q, --quiet           print only errors
  -v, --verbose         also print, on stderr, the commands and HTTP requests it runs
  --no-color            no color in what it prints (as NO_COLOR=1 does)

REST authentication:
  runtime 5 lets anonymous clients use 'user' endpoints (implicit user role)
  but needs an administrator for others, such as /rest/addons. After the REST
  API answers, `start` logs into the local Karaf console (runtime/bin/client
  as the distribution's console user openhab/habopen, 127.0.0.1:13617 only)
  and runs:
      openhab:users add admin <random password> administrator
      openhab:users addApiToken admin automation sandbox
  It writes the token to var/sandbox/api-token and the password to
  var/sandbox/admin-password, both mode 0600 and gitignored. A token that
  still works is reused on the next start. Send it as
      curl -H "Authorization: Bearer $(cat var/sandbox/api-token)" \
           http://127.0.0.1:13615/rest/addons
  and log into the UI as 'admin' with the stored password. --fresh discards
  both together with userdata.

first boot:
  With empty userdata, start first builds the OSGi cache with a separate
  server that gets no add-ons and must exit completely (about 20s). The
  distribution's own priming in runtime/bin/karaf races the real server
  and can leave add-ons that Karaf lists as installed without their bundles
  (Things UNINITIALIZED/HANDLER_MISSING_ERROR on every later start; only
  --fresh recovers). start then waits for the add-ons in conf's
  services/addons.cfg to install. If the start level stays below 30 or
  Things stay UNINITIALIZED/HANDLER_MISSING_ERROR or NOT_YET_READY for 60s
  after that, start restarts runtime once on the same userdata.

stopping:
  Karaf shutdown hangs for minutes (Jetty stopping its selectors in
  WebClientFactoryImpl.deactivate, jUPnP unsubscribing from every device),
  so stop sends SIGKILL after --timeout. runtime runs with Equinox saving its
  bundle database one second after a change, so a kill loses no add-on
  installed more than a few seconds earlier. If a killed sandbox does not
  start again normally, use start --fresh.

pairing:
  An Android TV pairs with the sandbox through thermite pair DEVICE
  --sandbox; its pairing is kept in userdata/androidtv/, so a --fresh start
  pairs again.

thermite completion

Print a completion script for bash, zsh or fish.

usage: thermite completion [-h] [--config DIR] SHELL

Print a script that teaches bash, zsh or fish to complete thermite's
command lines: every verb, each verb's actions, each verb's and action's
switches, the choices a switch or an argument takes, and file and directory
names where a switch takes a FILE or a DIR. It is built from the verbs' own
parsers, so it completes what this thermite has. Install it again after an
update that adds verbs or switches.

positional arguments:
  SHELL                 bash, zsh or fish

options:
  -h, --help            show this help message and exit
  --config, --site DIR  use this private configuration directory

switches every verb takes:
  -q, --quiet           print only errors
  -v, --verbose         also print, on stderr, the commands and HTTP requests it runs
  --no-color            no color in what it prints (as NO_COLOR=1 does)

installing it:
  bash  for this shell: source <(thermite completion bash)
        for every new one: thermite completion bash >
          ~/.local/share/bash-completion/completions/thermite
  zsh   save it as _thermite in a directory on $fpath, before compinit runs:
          thermite completion zsh > ~/.zfunc/_thermite
        with fpath+=(~/.zfunc) above compinit in ~/.zshrc
  fish  thermite completion fish > ~/.config/fish/completions/thermite.fish

  Each completes the installed command `thermite`; activate its environment
  or put its executable on PATH. Private configuration needs no launcher.

examples:
  thermite completion bash          the bash script; source <(thermite completion bash) uses it now
  thermite completion zsh > ~/.zfunc/_thermite
                                    zsh's, where compinit finds it
  thermite completion fish > ~/.config/fish/completions/thermite.fish
                                    fish's
