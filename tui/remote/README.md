# Terminal remote

Run `bin/thermite remote --mock` to explore a fictional house. Node.js and the locked blessed package are required.

Home shows your rooms and opens Remotes, Security, Cameras or Site. Use the arrow keys to choose, Enter to open, and `?` for the current page's keys. `Tab` changes panes, `PgUp`/`PgDn` scroll, `t` changes theme, and `q` quits. Pair devices with `F6` from Remotes.

Rooms through the day (`h` on Home or Remotes, or the link below Home's rooms) draws the House board's timeline from Grafana: one row per room, its confirmed source over the last 24 hours, not the one requested. A source is tan, with its name where the run is wide enough; Off is slate; Unknown, grey, is a room whose devices gave no readback; a dot is no data. Up and Down choose a room to list its latest runs. It reads the gateway's room history when it opens and every minute while open, and operates nothing. `--mock` draws a fictional day; explicit native testing mode has no gateway to read it from.

From any computer with thermite installed, such as a laptop, run `thermite tui`. It needs no private site: it opens the gateway at `https://thermite:13601`, the name most homes give their Thermite server, and reads the house's rooms and controls from it. Pass `--url` for another name or address, e.g. `thermite tui --url 192.0.2.50` for `https://192.0.2.50:13601`, or `HOST:PORT` for a gateway that `instance/host.yaml` moved off 13601 (`gateway: {port: N}`); with `--config DIR` selecting that private site, its port is the default. The remote is HTTPS only: pointed at a plain-HTTP port, such as a Guest port, it says so. The gateway's certificate comes from the server's private certificate authority, `tls-cert.pem` in its gateway root (`/srv/thermite/access` by default); on the server itself the installation's copy is used, and another computer passes a copy once with `--ca-file`, after which it is remembered for that address. An untrusted certificate stops with the file to copy; verification is never turned off.

For a real house from its private site, run `thermite remote --url https://thermite.example:13601`. Basic controls in unlocked rooms work without a login in either authentication mode. A room that is Off selects its Off bubble and draws no remote until a device bubble is chosen for its buttons. In a locked room the bubble for what it shows, Off included, carries a padlock (⚿) in place of its light and every other bubble is greyed out; choosing the padlocked bubble says why it is locked and, for a schedule, until when. The rooms panel and Home show ⚿ after a locked room's source. Only a lock the terminal has read greys its controls: if a room's lock cannot be read, Remotes says "Room lock status unknown" and still sends commands, which the server refuses in a locked room. To use an account's management permissions, sign in with `thermite access login --url https://thermite.example:13601 --user operator`. Use your own host and account. After changing inventory, run `thermite generate`; the terminal uses your site's generated house model. Credentials stay in an owner-only file.

With authentication enabled, administrators can lock the current room from Remotes with `K`, or with **Lock room** under Info (`i`). The server captures its current reported source or Off and holds it until manually unlocked, including across restarts. To lock on a particular source, right-click its bubble, or Off, or press `o` on it: the menu offers **Lock on** that source, **Unlock room** while manually locked, or **Lock until unlocked** on the bubble a schedule is holding. Locking on another source switches the room first and locks only once the room reports it. The manual lock takes precedence over schedules; releasing it resumes any current schedule. Other users see the lock status without an unlock control.

The terminal reconnects an event stream that has been silent for 15 s (the gateway sends a heartbeat every 5 s), reads the house afresh, and shows anything the gateway does not know as unknown. A command unanswered after 15 s (All off: 30 s) stops waiting and says it may still take effect.

When the terminal gives up waiting on the gateway (a lock read, a room command, an event stream or its first snapshot), or the gateway refuses an event stream, it counts that and reports the counts, never their content, to the gateway after its next answered request, and sends any it has not reported as it quits.

Security (F3) shows authentication status and the browser address for changing it. First setup uses a short-lived code generated on the host by `thermite access setup --config /path/to/access/config.json`, run from the staged release as the thermite service account. Changing authentication signs out every browser and terminal. Pairing, locks and room schedules require authentication. To elevate access, quit, sign in as an administrator with `thermite access login`, and reopen the terminal; an administrator can also make an account an administrator in Users (F8), after which that user must sign in again. Accounts are either administrators or ordinary accounts, which add camera media to what anyone can do in unlocked rooms. Explicit native testing mode cannot change authentication or secure direct runtime access.
